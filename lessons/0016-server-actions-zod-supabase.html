🌉 Bối cảnh thực tế: Vì Sao Core Service Không Thể Gọi Trực Tiếp Từ Trình Duyệt?

Ở Bài 11, chúng ta đã có LedgerService và ở Module 3 chúng ta có InventoryService. Cả hai service này đều chạy rất nhanh và an toàn trong môi trường kiểm thử.

Tuy nhiên, trên trình duyệt web của người dùng, bạn tuyệt đối không thể import và gọi trực tiếp các service này. Trình duyệt là môi trường công cộng của người dùng cuối. Nếu gọi trực tiếp, bạn sẽ làm lộ các khóa bảo mật bí mật của Supabase, và người dùng có thể dùng công cụ Inspect để sửa đổi số tiền thanh toán từ 2.500$ thành 1$! Chúng ta cần một Tầng Ứng Dụng (Application Layer) làm nhiệm vụ kiểm soát an ninh trên máy chủ.

Ý nghĩa và nhiệm vụ cụ thể của từng file:

📁 Phân công trách nhiệm trong thư mục `src/actions/`

  • billing.ts (Người điều phối): Hàm Server Action chạy trên máy chủ backend (chỉ thị 'use server'), phối hợp gọi InventoryService và LedgerService theo thứ tự chuẩn xác.
  • actions.test.ts (Kiểm thử tự động): Kiểm tra xem Server Action có bắt đúng lỗi khi nhận dữ liệu giả mạo hay không.

2. Giai đoạn 2: Thiết Lập Lá Chắn Zod (Zod Shield Pattern)

Nguyên tắc cốt lõi của bảo mật ứng dụng web: Không bao giờ tin tưởng dữ liệu gửi từ client.

Mở file src/actions/schemas.ts và cùng xem cách Zod bảo vệ hệ thống:

src/actions/schemas.ts — Khởi tạo Zod Schemas
import { z } from 'zod';

// Định nghĩa cấu trúc hợp lệ duy nhất của yêu cầu thanh toán đơn hàng
export const ProcessOrderPaymentSchema = z.object({
  orderId: z.string().min(1, 'Mã đơn hàng không được để trống'),
  amount: z.number().positive('Số tiền thanh toán phải lớn hơn 0'),
  reservationId: z.string().min(1, 'Mã giữ kho không được để trống'),
  taxAmount: z.number().nonnegative('Thuế không được âm').optional(),
});

// Tự động xuất kiểu dữ liệu TypeScript tương ứng
export type ProcessOrderPaymentInput = z.infer<typeof ProcessOrderPaymentSchema>;
💡 Kỹ thuật chuẩn: Dùng `safeParse` thay vì `parse`

Nếu dùng Schema.parse(), khi client gửi dữ liệu sai, Zod sẽ quăng lỗi văng ra ngoài làm sập trang web. Khi dùng Schema.safeParse(), Zod trả về kết quả an toàn:

  • Nếu hợp lệ: { success: true, data: ... }
  • Nếu có lỗi: { success: false, error: ... } giúp server phản hồi thông báo nhẹ nhàng về giao diện mà không bị crash.

3. Giai đoạn 3: Điều Phối Multi-domain Server Action Giữa Kho & Kế Toán

Khi người dùng bấm "Thanh toán", hai sự kiện phải diễn ra đồng thời: Kho phải chốt trừ hàng và Kế toán phải ghi nhận tiền.

Hộp Prompt Mẫu Chỉ Đạo AI Viết Server Action:

Prompt chỉ đạo AI tạo Server Action
Hãy viết Server Action processOrderPaymentAction tại file src/actions/billing.ts:

1. Đặt chỉ thị 'use server' ở đầu file.
2. Tham số input nhận vào kiểu unknown để ép buộc phải kiểm tra an ninh qua ProcessOrderPaymentSchema.safeParse().
3. Điều phối theo đúng chu trình 3 bước:
   - Bước 1: Cấp hóa đơn chính thức (ledgerService.createInvoice).
   - Bước 2: Chốt giữ hàng sang tồn kho vật lý (inventoryService.settleReservation(reservationId, 'COMMIT')).
   - Bước 3: Hạch toán dòng tiền (ledgerService.recordOrderPayment: Nợ 112, Có 511).
4. Bọc toàn bộ trong try/catch và trả về cấu trúc thống nhất { success: boolean; data?: ...; error?: string }.
src/actions/billing.ts — Hiện thực hóa Server Action
'use server';

export async function processOrderPaymentAction(
  input: unknown,
  inventoryService: InventoryService,
  ledgerService: LedgerService
): Promise<ActionResult<PaymentSuccessData>> {
  // 1. Soi an ninh dữ liệu
  const parsed = ProcessOrderPaymentSchema.safeParse(input);
  if (!parsed.success) {
    return { success: false, error: parsed.error.issues.map(i => i.message).join('; ') };
  }

  const { orderId, amount, reservationId, taxAmount } = parsed.data;

  try {
    // 2. Bước 1: Cấp hóa đơn
    const invoice = await ledgerService.createInvoice({
      orderId,
      subtotal: amount,
      taxAmount: taxAmount ?? 0,
    });

    // 3. Bước 2: Chốt kho (Physical Stock giảm đi)
    await inventoryService.settleReservation(reservationId, 'COMMIT');

    // 4. Bước 3: Hạch toán Sổ cái Kế toán (Nợ 112 Tiền gửi, Có 511 Doanh thu)
    const { transaction } = await ledgerService.recordOrderPayment(
      orderId,
      invoice.totalAmount,
      invoice.id
    );

    invoice.status = 'PAID';

    return { success: true, data: { invoice, transactionId: transaction.id } };
  } catch (err: any) {
    return { success: false, error: err.message || 'Lỗi xử lý thanh toán đơn hàng' };
  }
}

4. Giai đoạn 4: Cưỡng Chế Append-only Bằng Supabase Row Level Security (RLS)

Để ngăn chặn bất kỳ ai can thiệp trực tiếp vào database để sửa hoặc xóa số tiền, chúng ta thiết lập chính sách RLS tại tầng PostgreSQL:

PostgreSQL Migration — Khóa chặt bảng ledger_entries
-- 1. Bật tính năng Row Level Security
ALTER TABLE ledger_entries ENABLE ROW LEVEL SECURITY;

-- 2. Chỉ cho phép THÊM MỚI bút toán
CREATE POLICY "Cho phep them moi but toan" ON ledger_entries
    FOR INSERT WITH CHECK (true);

-- 3. Chỉ cho phép ĐỌC để xem báo cáo
CREATE POLICY "Cho phep doc but toan" ON ledger_entries
    FOR SELECT USING (true);

-- TUYỆT ĐỐI KHÔNG TẠO POLICY CHO UPDATE HAY DELETE!
-- Bất kỳ lệnh sửa hoặc xóa nào đều sẽ bị PostgreSQL từ chối thẳng thừng.
