Module 3 · Bài 09

/implement-spec — Kỹ Nghệ Thực Thi Đặc Tả: Task Graph & Subagents

Chuyển hóa tài liệu kỹ thuật thành Đồ thị Nhiệm vụ (DAG), xác định tập Frontier và điều phối các Implementer Subagents độc lập trên Git Worktrees.

⏱ ~15 phút · 🎯 Mục tiêu: Làm chủ skill /implement-spec, nắm vững kỹ thuật quản lý đồ thị phụ thuộc giữa các tickets và tự động hóa thi công mà không làm tràn Context Window.

🌉 Bối cảnh kỹ thuật: Bẫy "Làm tất cả trong một lần chat" (Context Bloat)

Sau khi hoàn tất bản đặc tả specs/inventory-and-order.md và phân rã thành 5 tickets ở Bài 06, một sai lầm phổ biến của người mới dùng AI coding là nạp toàn bộ file spec vào prompt và ra lệnh: "Hãy code hết toàn bộ spec này cho tôi".

Cách làm này luôn thất bại vì hai lý do:

  1. Context Degradation: Sau vài nghìn dòng code sinh ra, bộ nhớ của AI bị bão hòa (Attention Dilution). AI bắt đầu quên các ràng buộc ở đầu spec, sinh code lặp, hoặc âm thầm xóa bỏ các kiểm tra quan trọng.
  2. Xung đột thứ tự phụ thuộc: AI viết tầng UI trước khi tầng Service hoàn thành, dẫn đến việc phải liên tục sửa đi sửa lại các hàm giả định.

Skill /implement-spec giải quyết triệt để vấn đề này bằng mô hình Task Graph & Frontier Subagents.

1. Mô Hình Task Graph: Biến Danh Sách Tickets Thành Đồ Thị Phụ Thuộc

Thay vì xem các task như một danh sách phẳng từ trên xuống dưới, /implement-spec tổ chức chúng thành một đồ thị có hướng không chu trình (Directed Acyclic Graph - DAG):

Mô hình Task Graph và Tập Frontier cho Phân hệ Kho
[Ticket 01: In-Memory Repo Seam] ◄── [TẬP FRONTIER: Sẵn sàng làm ngay (In-degree = 0)]
            │
            ▼
[Ticket 02: Stock Reservation Service] (Chờ Ticket 01)
            │
            ├──────────────────────────────────────────┐
            ▼                                          ▼
[Ticket 03: Order State Machine]             [Ticket 04: Supabase Postgres Adapter]
(Chờ Ticket 02)                              (Chờ Ticket 02)
            │                                          │
            └────────────────────┬─────────────────────┘
                                 ▼
                     [Ticket 05: Server Actions E2E] (Chờ Ticket 03 & 04)

Thuật toán vận hành cốt lõi:

  • Tập Frontier: Là tập hợp các task hiện đang có số lượng phụ thuộc bằng 0 (in-degree = 0). Chỉ những task thuộc Frontier mới được phép đưa vào thi công.
  • Mở khóa tuần tự (Unblocking): Khi Ticket 01 hoàn thành và kiểm thử xanh 100%, Ticket 02 lập tức trở thành Frontier mới.
  • Thi công song song (Parallel execution): Khi Ticket 02 hoàn thành, cả Ticket 03 và Ticket 04 cùng lúc bước vào Frontier, cho phép phân bổ 2 subagents thực thi song song hoàn toàn độc lập!

2. Cách Ly Không Gian Làm Việc Bằng Git Worktrees

Để ngăn chặn tình trạng hai subagent cùng ghi đè lên thư mục làm việc (dirty working tree), /implement-spec sử dụng Git Worktrees:

terminal (bash)
# Tạo worktree riêng biệt cho Ticket 01
git worktree add .worktrees/ticket-01-in-memory-repo -b feat/ticket-01-in-memory

# Sau khi hoàn thành và verify test xanh 100%, merge lại nhánh chính và dọn dẹp
git merge feat/ticket-01-in-memory
git worktree remove .worktrees/ticket-01-in-memory-repo

4. Ranh Giới Giữa `/implement-spec` và `/implement`

Hãy phân biệt rõ vai trò của hai kỹ năng này trong bộ công cụ của Matt Pocock:

Tiêu chí /implement-spec (Nhạc trưởng điều phối) /implement (Thợ thi công TDD)
Phạm vi (Scope) Toàn bộ đặc tả hệ thống và đồ thị phụ thuộc giữa nhiều tickets. Duy nhất MỘT ticket hoặc MỘT vertical slice cụ thể.
Cơ chế hoạt động Xây dựng Task Graph, quản lý trạng thái Frontier, điều phối subagents. Vận hành chu trình Red - Green - Refactor, type checking, viết mã nguồn.
Mục tiêu cốt lõi Đảm bảo không bỏ sót task, tránh context rot, tối ưu hóa thứ tự thi công. Đảm bảo 100% test case pass, mã nguồn sạch đẹp, tuân thủ Seam interface.
