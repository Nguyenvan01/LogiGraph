Sau khi hoàn thành hai bước quan trọng: xử lý Race Condition ở Bài 14 và Senior Code Review 2 trục độc lập ở Bài 15, hệ thống VibeCoding ERP Mini đã sẵn sàng để phát hành phiên bản chính thức đầu tiên: Release v1.0.

Tuy nhiên, một chu trình kỹ thuật phần mềm chuẩn mực không kết thúc khi code đã chạy xong. Hai bước cuối cùng để hoàn thiện vòng đời phát triển là:

  • Đóng gói Pull Request (`/pr`): Trình bày thay đổi cho đồng nghiệp và các bên liên quan một cách súc tích, cung cấp bằng chứng kiểm thử thực tế và đánh giá rủi ro rõ ràng.
  • Đúc kết kinh nghiệm (`/retro`): Rà soát lại môi trường làm việc, con trỏ định hướng file và các rào chắn tự động để các phiên làm việc tiếp theo của coding agent đạt hiệu suất cao hơn.

1. Nghệ thuật Viết Pull Request theo Chuẩn Matt Pocock (/pr)

Một PR body kém chất lượng thường mắc phải hai thái cực: hoặc quá sơ sài không có thông tin, hoặc quá dài dòng với những lời mở đầu không cần thiết. Kỹ năng pr của Matt Pocock thiết lập một template 3 phần chuẩn mực, tập trung vào bản chất:

Template PR Body Chuẩn của Matt Pocock (Dex Horthy / Show-me)
## Summary

<diagram, diff-sketch, call-tree, hoặc shallow file tree>

## Evidence

- **Before:** <screenshot, log, hoặc failing test run>
  **After:** <screenshot, log, hoặc passing test run>

## Merge Danger

**Door:** <one-way hoặc two-way>

<mô tả đánh giá khả năng hoàn tác>

**Blast Radius:** <đánh giá phạm vi ảnh hưởng trong một từ>

<mô tả hệ quả tiềm ẩn đối với các thành phần xung quanh>
🚪 Khái niệm One-way Door vs Two-way Door trong Đánh giá Rủi ro

Lấy cảm hứng từ triết lý ra quyết định của Jeff Bezos, việc phân loại quyết định sáp nhập mã nguồn thành hai loại cửa giúp đội ngũ kỹ thuật có chiến lược review phù hợp:

  • Two-way Door (Cửa hai chiều): Quyết định có thể dễ dàng đảo ngược hoặc rollback với chi phí thấp nếu phát sinh sự cố. Ví dụ: thêm một hàm mới, bổ sung adapter, hoặc cập nhật logic tầng ứng dụng có bảo vệ bằng feature flag. Các PR này có rủi ro thấp.
  • One-way Door (Cửa một chiều): Quyết định khó hoặc không thể đảo ngược mà không gây gián đoạn hệ thống hoặc mất dữ liệu. Ví dụ: xóa cột cơ sở dữ liệu, chạy migration thay đổi kiểu dữ liệu bảng lớn, hoặc thay đổi giao thức xác thực. Các PR này đòi hỏi kiểm thử thận trọng và kế hoạch dự phòng chi tiết.

User Action (UI / Server Action)

  ├── processOrderPaymentAction()
  │     ├── commitReservation() ──► Trừ kho vật lý

  │     └── postTransaction()  ──► Debit 112 (Bank) / Credit 511 (Revenue)
  └── getTrialBalanceAction()  ──► Bảng cân đối thử nghiệm (Σ Debit === Σ Credit)

## Evidence
- Before: Check-Then-Act gây rủi ro Over-selling khi có request đồng thời; chưa có sổ cái kép.
- After: 35/35 automated tests trong Vitest pass trong 159ms; typecheck 0 lỗi; test Concurrency
  chứng minh 10 requests đồng thời tranh mua 2 sản phẩm: đúng 2 request thành công, 8 request
  bị từ chối an toàn, tồn kho không bao giờ âm.

## Merge Danger
**Door:** Two-way door
Toàn bộ logic được bao bọc sau Seams (IInventoryRepository, ILedgerRepository). Dữ liệu có
Check Constraints bảo vệ tính tương thích ngược, dễ dàng hoàn tác hoặc hoán đổi adapter.

**Blast Radius:** Low
Phạm vi tác động giới hạn trong các module nội bộ (inventory, ledger, actions).

3. Quản lý Phiên bản với Semantic Versioning & Changelog

Một dự án mã nguồn chuyên nghiệp cần một lịch sử thay đổi rõ ràng. File CHANGELOG.md được xây dựng theo chuẩn Keep a Changelog và tuân thủ Semantic Versioning (SemVer):

Quy tắc Đánh số Phiên bản Semantic Versioning (MAJOR.MINOR.PATCH)
Phiên bản: v1.0.0
           │ │ │
           │ │ └── PATCH: Vá lỗi tương thích ngược (Bug fixes)
           │ └──── MINOR: Bổ sung tính năng mới tương thích ngược (New features)
           └────── MAJOR: Thay đổi lớn phá vỡ tính tương thích ngược (Breaking changes)

4. Phương pháp luận Retrospective cho Coding Agent (/retro)

Trong kỹ nghệ lập trình cùng AI (Agentic Engineering), mục tiêu của một buổi Retrospective không phải là đánh giá hiệu suất con người, mà là cải thiện môi trường làm việc (Environment) của coding agent để các phiên làm việc tiếp theo diễn ra mượt mà và chính xác hơn.

⚖️ Nguyên tắc: Implementation Agent vs Review Agent (Áp lực Ngữ cảnh)

Matt Pocock chỉ ra một sự thật quan trọng về quản lý Token Budget:

  • Implementation Agent: Chịu áp lực ngữ cảnh (Context Pressure) lớn nhất. Agent này phải khám phá thư mục, đọc nhiều file, viết code và debug lỗi. Cần giữ steering files ngắn gọn để dành token cho agent này suy luận.
  • Review Agent: Chịu áp lực ngữ cảnh thấp nhất. Agent này chỉ nhận diff của commit/PR, không phải khám phá hay viết lại toàn bộ hệ thống. Do đó, Review Agent là đối tượng phù hợp nhất để chịu trách nhiệm kiểm tra các quy chuẩn kiến trúc trong CODING_STANDARDS.md.
