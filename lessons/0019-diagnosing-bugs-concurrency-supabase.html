1. Bản chất của Concurrency Bug: Cạm bẫy Check-Then-Act

Một lỗi phổ biến trong các ứng dụng web là mẫu hình Check-Then-Act hoặc Read-Modify-Write diễn ra tại tầng ứng dụng:

Mã nguồn có lỗ hổng Race Condition (Vulnerable Implementation)
// Bước 1: Đọc tồn kho khả dụng từ Database View (Check)
const balance = await this.getStockBalance(productId);
if (!balance || balance.availableStock < quantity) {
  throw new InsufficientStockError(productId, quantity, balance?.availableStock ?? 0);
}

// Giữa bước 1 và bước 2 tồn tại Network Latency và I/O round-trip (10ms - 50ms)

// Bước 2: Ghi nhận bản ghi giữ hàng vào Database (Act)
await this.client.from('stock_reservations').insert({
  product_id: productId,
  quantity,
  status: 'ACTIVE',
  expires_at: expiresAt.toISOString(),
});

Hãy xem xét dòng thời gian khi hai yêu cầu (Request A và Request B) cùng đến máy chủ cách nhau 2 mili-giây đối với một sản phẩm chỉ còn duy nhất 1 đơn vị tồn kho khả dụng:

2. Kỷ luật Chẩn đoán Lỗi của Matt Pocock (diagnosing-bugs)

Khi đối mặt với một bug khó như Race Condition, phản xạ tự nhiên của nhiều lập trình viên là lập tức nhảy vào đọc code, suy đoán nguyên nhân và thử sửa bừa (Trial and Error). Kỹ năng diagnosing-bugs của Matt Pocock thiết lập một kỷ luật hoàn toàn trái ngược gồm 6 giai đoạn rõ ràng:

📋 6 Giai đoạn Chẩn đoán Lỗi theo Chuẩn Matt Pocock
  1. Phase 1: Build a Feedback Loop: Thiết kế một lệnh hoặc kịch bản kiểm thử duy nhất có đặc tính Fast, Deterministic và Red-capable (có khả năng fail đỏ chính xác trên lỗi này). "No red-capable command, no Phase 2."
  2. Phase 2: Reproduce + Minimise: Chạy loop, quan sát lỗi xuất hiện. Sau đó loại bỏ từng biến số phụ cho đến khi mọi yếu tố còn lại đều là load-bearing (thiếu nó thì lỗi không xảy ra).
  3. Phase 3: Hypothesise: Liệt kê 3 đến 5 giả thuyết có thể kiểm chứng (Falsifiable) theo cú pháp: "If <X> is the cause, then <changing Y> will make the bug disappear / <changing Z> will make it worse."
  4. Phase 4: Instrument: Đặt các điểm đo có chủ đích, gắn Unique Prefix ví dụ [DEBUG-...] để sau này dọn sạch bằng một lệnh grep. Chỉ thay đổi một biến số duy nhất tại một thời điểm.
  5. Phase 5: Fix + Regression Test: Viết test hồi quy tại đúng Seam kỹ thuật trước khi sửa code. Áp dụng giải pháp, quan sát test chuyển từ đỏ sang xanh. Chạy lại feedback loop ban đầu.
  6. Phase 6: Cleanup: Xóa toàn bộ probe debug, kiểm tra toàn bộ test suite và ghi lại giả thuyết đúng vào commit message hoặc tài liệu bàn giao.

3. Phân Tích Kiến Trúc: Đánh Giá 3 Chiến Lược Xử Lý Concurrency Trên PostgreSQL

🤔 Tại sao không dùng In-memory Mutex ở tầng Node.js?

Câu hỏi: Trong Node.js hoặc Next.js Server Actions, chúng ta có thể tạo một In-memory Mutex hoặc biến cờ để ngăn hai request cùng vào một đoạn mã xử lý tồn kho hay không?

Bản chất kỹ thuật: Trong kiến trúc Web hiện đại và Cloud Serverless (Next.js triển khai trên Vercel, Docker hoặc Kubernetes), các Server Actions được thực thi trên nhiều Worker processes, các container độc lập hoặc các Serverless Functions phân tán trên toàn cầu.

Một khóa trong RAM của Process A hoàn toàn vô hiệu đối với Process B đang chạy trên một máy chủ khác. Single Source of Truth giữa các tiến trình chính là PostgreSQL Database trên Supabase. Do đó, việc bảo vệ bất biến dữ liệu bắt buộc phải được giải quyết tại tầng cơ sở dữ liệu.

💡 Đánh Giá 3 Chiến Lược Xử Lý Concurrency Trên PostgreSQL
Chiến lược Cơ chế hoạt động Ưu điểm Nhược điểm & Ứng dụng
Pessimistic Locking (SELECT FOR UPDATE) Khóa dòng sản phẩm trên bảng products ngay từ đầu transaction. Các request khác phải xếp hàng chờ. Ngăn chặn Race Condition 100%; không phát sinh lỗi retry từ client; thời gian giữ khóa cực ngắn (< 5ms). Lựa chọn tối ưu cho bài toán Flash Sale và quản lý tồn kho số lượng ít.
Optimistic Concurrency Control (OCC) Thêm cột version hoặc so sánh giá trị cũ khi update (UPDATE ... WHERE version = v). Không khóa dữ liệu, hiệu năng cao khi contention thấp. Khi nhiều người cùng tranh mua 1 món hàng, hầu hết các request bị abort và phải retry liên tục gây lãng phí tài nguyên.
Serializable Isolation Level PostgreSQL tự động phát hiện Serialization Anomalies và ném lỗi 40001 (serialization_failure). Tách bạch hoàn toàn logic khóa khỏi câu truy vấn. Ứng dụng bắt buộc phải triển khai cơ chế Retry Loop phức tạp; chi phí tài nguyên máy chủ cao.

4. Hiện thực hóa Giải pháp: PostgreSQL Stored Procedure

Để giải quyết triệt để vấn đề, chúng ta gom toàn bộ thao tác Check và Act vào một PostgreSQL Function duy nhất, chạy dưới một transaction có Row-level Lock:

Migration: supabase/migrations/20260928000004_atomic_inventory_concurrency.sql
CREATE OR REPLACE FUNCTION reserve_stock_atomic(
    p_product_id UUID,
    p_quantity INTEGER,
    p_order_id UUID DEFAULT NULL,
    p_ttl_minutes INTEGER DEFAULT 15
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
    v_physical_stock INTEGER;
    v_active_reservations INTEGER;
    v_available_stock INTEGER;
    v_reservation_id UUID;
    v_expires_at TIMESTAMPTZ;
    v_now TIMESTAMPTZ := clock_timestamp();
BEGIN
    -- 1. Khóa dòng sản phẩm bằng Row-Level Exclusive Lock (FOR UPDATE)
    SELECT stock INTO v_physical_stock
    FROM products
    WHERE id = p_product_id
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Product with ID % not found', p_product_id
            USING ERRCODE = 'P0002';
    END IF;

    -- 2. Tính toán active reservations trong cùng một lock context
    SELECT COALESCE(SUM(quantity), 0)::INTEGER INTO v_active_reservations
    FROM stock_reservations
    WHERE product_id = p_product_id
      AND status = 'ACTIVE'
      AND expires_at > v_now;

    -- 3. Tính tồn kho khả dụng thực tế
    v_available_stock := v_physical_stock - v_active_reservations;

    -- 4. Kiểm tra điều kiện tồn kho khả dụng
    IF v_available_stock < p_quantity THEN
        RAISE EXCEPTION 'Insufficient stock for product %: requested %, available %',
            p_product_id, p_quantity, v_available_stock
            USING ERRCODE = 'P0001';
    END IF;

    -- 5. Thực hiện chốt bản ghi giữ hàng mới
    v_reservation_id := gen_random_uuid();
    v_expires_at := v_now + (p_ttl_minutes || ' minutes')::INTERVAL;

    INSERT INTO stock_reservations (
        id, order_id, product_id, quantity, status, expires_at, created_at, updated_at
    ) VALUES (
        v_reservation_id, p_order_id, p_product_id, p_quantity, 'ACTIVE', v_expires_at, v_now, v_now
    );

    RETURN jsonb_build_object(
        'id', v_reservation_id,
        'productId', p_product_id,
        'orderId', p_order_id,
        'quantity', p_quantity,
        'status', 'ACTIVE',
        'expiresAt', v_expires_at,
        'createdAt', v_now,
        'updatedAt', v_now
    );
END;
$$;

🎓 Đúc kết Bài 19: Kỷ luật Kỹ thuật khi Xử lý Bug Concurrency
