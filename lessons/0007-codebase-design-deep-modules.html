1. Triết lý Deep Modules của John Ousterhout

Trong cuốn sách nổi tiếng A Philosophy of Software Design, Giáo sư John Ousterhout phân biệt hai loại mô-đun phần mềm:

So sánh trực quan: Deep Module vs Shallow Module
        DEEP MODULE (Nên dùng)                      SHALLOW MODULE (Nên tránh)
┌─────────────────────────────────────┐       ┌─────────────────────────────────────┐
│    Interface nhỏ (3 hàm đơn giản)   │       │   Interface lớn (hàng chục hàm API) │
├─────────────────────────────────────┤       ├─────────────────────────────────────┤
│                                     │       │                                     │
│  Implementation sâu & giàu năng lực │       │   Implementation nông (chỉ chuyển   │
│  (Ẩn giấu TTL, Invariant, Concurrency│       │   tiếp dữ liệu đơn thuần)           │
│   và kiểm soát lỗi bên trong)       │       │                                     │
│                                     │       └─────────────────────────────────────┘
└─────────────────────────────────────┘

Matt Pocock định nghĩa lại các khái niệm then chốt theo góc nhìn Kỹ nghệ Agent:

  • Depth: Tỷ lệ Leverage tại bề mặt Interface. Khả năng mà caller có thể điều khiển trên mỗi đơn vị kiến thức họ phải ghi nhớ. Một mô-đun được gọi là Deep khi nó cung cấp năng lực mạnh mẽ đằng sau một Interface nhỏ gọn.
  • Leverage cho Caller: Người gọi chỉ cần học 3 hàm đơn giản nhưng giải quyết được toàn bộ bài toán phức tạp về tranh chấp kho và hết hạn thanh toán.
  • Locality cho Maintainer: Khi có bug hoặc cần tối ưu thuật toán trừ kho, kỹ sư chỉ cần sửa tại MỘT vị trí duy nhất bên trong implementation mà không làm thay đổi bất kỳ dòng code nào ở phía caller.
  • The Deletion Test: Hãy thử tưởng tượng nếu xóa module này đi: nếu độ phức tạp biến mất thì đó là một pass-through nông cạn; nếu độ phức tạp bùng nổ tràn lan sang hàng chục caller thì đó chính là một Deep Module thực thụ đang gánh vác trách nhiệm lớn.

2. Thiết kế Seams & 2 Adapters

Theo Michael Feathers (Working Effectively with Legacy Code), Seam là vị trí cho phép thay đổi hành vi của chương trình mà không cần chỉnh sửa mã nguồn tại vị trí đó.

💡 Định luật Seam của Matt Pocock

"One adapter means a hypothetical seam. Two adapters means a real one."
(Nếu chỉ có một Adapter duy nhất, seam đó mới chỉ là giả định trên lý thuyết. Khi có hai Adapters cùng thỏa mãn Interface, seam mới thực sự hình thành.)

Trong dự án VibeCoding ERP, chúng ta đã thiết lập Seam chính thức tại interface IInventoryRepository và thi công đúng 2 Adapters:

Tên Adapter Vị trí file Mục đích & Môi trường hoạt động
InMemoryInventoryRepository adapters/in-memory.ts Sử dụng Map trong bộ nhớ. Dành riêng cho Unit Tests bằng Vitest. Thời gian chạy < 5ms, không cần Internet, không cần Supabase.
SupabaseInventoryRepository adapters/supabase.ts Thực thi các câu lệnh SQL nguyên tử kết hợp ràng buộc CHECK (stock >= 0) trên Supabase PostgreSQL. Dùng cho Production và Integration Tests.

3. Bóc tách Interface 3 Hàm của InventoryService

Đúng theo yêu cầu kiến trúc của Bài 07, bề mặt công khai của src/modules/inventory/index.ts được thu gọn tối đa vào 3 hàm nghiệp vụ:

src/modules/inventory/index.ts — Deep Interface 3 hàm
export class InventoryService {
  constructor(private readonly repo: IInventoryRepository) {}

  /**
   * 1. Tra cứu tồn kho khả dụng thời gian thực
   * Bảo toàn Invariant: availableStock = physicalStock - activeReservations
   */
  public async getAvailableStock(productId: string): Promise<number>;

  /**
   * 2. Tạm giữ tồn kho trong 15 phút TTL
   * Tự động kiểm tra khả dụng, quăng lỗi InsufficientStockError nếu thiếu hàng
   */
  public async reserveStock(productId: string, quantity: number, orderId?: string): Promise<StockReservation>;

  /**
   * 3. Quyết toán đợt giữ hàng (Settle)
   * - 'COMMIT': Khách thanh toán -> trừ vĩnh viễn vào kho vật lý
   * - 'RELEASE': Hủy đơn hoặc hết hạn TTL -> hoàn trả kho khả dụng
   */
  public async settleReservation(reservationId: string, action: 'COMMIT' | 'RELEASE', reason?: string): Promise<void>;
}

Cấu trúc thư mục theo chuẩn /setup-ts-deep-modules

Toàn bộ mã nguồn được tổ chức theo cấu trúc khép kín, ngăn chặn việc import bừa bãi từ bên ngoài:

Cấu trúc mã nguồn tại src/modules/inventory/
src/modules/inventory/
├── index.ts          # Public surface duy nhất của module
├── domain/           # Thư mục nội bộ: Types, Domain Errors
│   ├── types.ts
│   └── errors.ts
└── adapters/         # Thư mục nội bộ: 2 Adapters ở Seam
    ├── in-memory.ts  # InMemory Adapter (Vitest)
    └── supabase.ts   # Supabase Postgres Adapter (Production)
