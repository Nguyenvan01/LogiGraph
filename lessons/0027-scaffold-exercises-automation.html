🌉 Bối cảnh kỹ thuật: Từ Khung Sư Phạm Sang Bài Tập Thực Hành Thật

Ở Bài 26, chúng ta đã nắm được kiến trúc không gian học tập có trạng thái với /teach. Tuy nhiên, cách tốt nhất để một lập trình viên học sâu một công nghệ (như TypeScript hay Next.js) không phải là đọc văn bản, mà là tự tay giải quyết các bài tập code thực tế.

Nếu bạn phải tự tay gõ lệnh tạo thư mục cho 50 bài tập, tạo file problem/, solution/, readme.md thủ công, bạn sẽ mất hàng tuần trời cho những thao tác lặp đi lặp lại. Kỹ năng /scaffold-exercises của Matt Pocock giải quyết việc này chỉ trong vài giây thông qua quy trình Plan-to-Scaffold tự động.

1. Cấu Trúc 3 Thư Mục Tiêu Chuẩn Cho Mọi Bài Tập

Matt Pocock quy chuẩn mỗi bài tập lập trình thực hành luôn được tổ chức thành 3 thư mục con chuyên biệt:

Cấu trúc Exercise Variants
exercises/
└── 01-inventory-fundamentals/                 # Thư mục Section: XX-section-name
    └── 01.01-stock-reservation-ttl/           # Thư mục Exercise: XX.YY-exercise-name
        ├── problem/                           # KHÔNG GIAN HỌC VIÊN: Chứa code có TODOs và test case FAIL
        │   ├── main.ts
        │   └── readme.md
        ├── solution/                          # LỜI GIẢI THAM CHIẾU: Code hoàn chỉnh đạt 100% test PASS
        │   ├── main.ts
        │   └── readme.md
        └── explainer/                         # GIẢI THÍCH LÝ THUYẾT: Tài liệu phân tích nguyên lý, không có TODOs
            └── readme.md
  • problem/: Nơi học viên mở ra để làm bài. Luôn chứa các đoạn code còn dang dở (// TODO: Implement stock reservation logic) và các bài test đang ở trạng thái FAIL.
  • solution/: Mã nguồn giải pháp chuẩn mực của tác giả. Học viên có thể tham chiếu khi bị bế tắc để so sánh với cách giải của mình.
  • explainer/: Tài liệu lý thuyết ngắn gọn giải thích lý do tại sao giải pháp đó lại tối ưu (Trade-offs, Invariants, Performance).

2. Quy Trình Plan-to-Scaffold: Từ Dàn Bài Đến Mã Nguồn Trong 5 Bước

Khi bạn cung cấp một dàn bài văn bản (Plan), /scaffold-exercises thực thi tuần tự 5 bước tự động:

Quy trình 5 bước Plan-to-Scaffold
[1. Parse Plan] ──► [2. mkdir -p] ──► [3. Stub Readmes] ──► [4. Run Linter] ──► [5. Git Commit]
 Trích xuất tên      Tự động tạo       Sinh file readme      Kiểm tra vi phạm      Bảo toàn lịch sử
 sections & bài tập  cây thư mục       và main.ts stubs      theo bộ quy tắc       bằng git commit
  1. Parse the plan: Trích xuất tên section (01-inventory), tên bài tập (01.01-ttl) và các biến thể cần tạo.
  2. Create directories: Chạy lệnh mkdir -p tạo hàng loạt thư mục chỉ trong một tích tắc.
  3. Create stub readmes: Sinh file readme.md tối thiểu có tiêu đề và mô tả ngắn gọn (không để file rỗng).
  4. Run lint: Chạy công cụ kiểm chuẩn nội bộ để đảm bảo không có file rác (như .gitkeep), không có link hỏng.
  5. Fix & Commit: Tự động sửa các lỗi linter phát hiện và lưu commit sạch sẽ vào Git.

3. Nghệ Thuật Đổi Số Bài Tập Bằng `git mv`

Khi bạn cần chèn thêm một bài học mới vào giữa khóa học (ví dụ chèn Bài 01.02 vào giữa 01.01 và 01.02 cũ), nếu dùng lệnh mv thông thường, Git sẽ hiểu là bạn xóa thư mục cũ và tạo thư mục mới, làm mất toàn bộ lịch sử commit trước đó!

terminal (bash) — Quy chuẩn đổi số bài tập
# ❌ SAI: Dùng mv thông thường làm mất git history
mv exercises/01-inventory/01.02-state-machine exercises/01-inventory/01.03-state-machine

# ✅ ĐÚNG: Luôn dùng git mv để bảo toàn 100% lịch sử commit và diffs
git mv exercises/01-inventory/01.02-state-machine exercises/01-inventory/01.03-state-machine

4. Hộp Prompt Thực Chiến: Dựng Khung Bài Tập TDD

Bạn ra lệnh cho AI dựng khung hàng loạt bài tập cho một phân hệ mới:

Prompt gọi /scaffold-exercises
/scaffold-exercises "Dựng khung các bài tập thực hành cho Section 02: Double-Entry Ledger:
- 02.01 Basic Account Invariants (problem + solution + explainer)
- 02.02 Debit Credit Balance Verification (problem + solution)
- 02.03 Compensatory Reversal Mechanism (explainer)
Tạo đầy đủ readme.md và main.ts stubs, sau đó chạy kiểm chuẩn linter và commit bằng git."

🧠 Trắc nghiệm củng cố

Câu 1. Tại sao mỗi thư mục bài tập của học viên (problem/) bắt buộc phải có test case ở trạng thái FAIL khi mới bắt đầu?
Câu 2. Khi cần đánh số lại hoặc di chuyển các bài tập trong khóa học, tại sao bắt buộc phải dùng `git mv` thay vì `mv` thông thường?
