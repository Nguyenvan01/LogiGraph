Đồng thời, khi làm việc trong nhóm phát triển phân tán hoặc tích hợp nhiều nhánh, Merge Conflict thường xuyên xuất hiện. Bài học này thực hành hai kỹ năng: /code-review và /resolving-merge-conflicts.

1. Nguyên lý Code Review 2 Trục Độc lập

Một vấn đề thường gặp khi review code là gộp chung tất cả nhận xét vào một danh sách duy nhất. Khi đó, các thảo luận về cú pháp có thể che khuất các sai lệch về logic nghiệp vụ.

⚖️ Bốn Tình huống Tương quan giữa Standards và Spec
Trường hợp Trục Standards Trục Spec Hệ quả thực tế
1. Phù hợp PASS PASS Kiến trúc rõ ràng, hiện thực hóa chính xác nghiệp vụ. Đủ điều kiện merge.
2. Sai lệch Spec PASS FAIL Code viết đúng chuẩn kiến trúc nhưng giải quyết sai bài toán hoặc thiếu yêu cầu trong spec.
3. Nợ Kỹ thuật FAIL PASS Đúng logic nghiệp vụ nhưng coupling chặt và vi phạm tiêu chuẩn thiết kế, gây khó khăn cho việc bảo trì.
4. Từ chối FAIL FAIL Vi phạm quy chuẩn dự án và sai lệch yêu cầu chức năng. Yêu cầu sửa đổi hoàn toàn.

Kỹ năng code-review của Matt Pocock giải quyết vấn đề này bằng cách chạy hai đánh giá độc lập:

  • Trục Standards: So sánh mã nguồn với tài liệu quy chuẩn dự án (CODING_STANDARDS.md, CONTEXT.md) và bộ lọc 12 Fowler Code Smells.
  • Trục Spec: Đối soát mã nguồn với bản đặc tả kỹ thuật gốc (specs/) để tìm ra 3 nhóm lỗi: Requirements bị thiếu, Scope Creep tự phát, hoặc yêu cầu bị làm sai logic.

2. Bảng Tra cứu 12 Fowler Code Smells Baseline

Khi một dự án chưa có tài liệu quy chuẩn chi tiết, Trục Standards luôn sử dụng danh sách 12 Code Smells kinh điển từ cuốn sách Refactoring của Martin Fowler làm thước đo chuẩn mực:

Bảng Đối chiếu 12 Fowler Code Smells & Hướng Xử lý
Code Smell               │ Bản chất nhận diện                          │ Hướng tái cấu trúc chuẩn
────────────────────────┼─────────────────────────────────────────────┼────────────────────────────────────────────
1. Mysterious Name      │ Tên biến, hàm không tiết lộ ý định thực sự. │ Đổi tên theo Ubiquitous Language.
2. Duplicated Code      │ Cùng một khối logic xuất hiện ở nhiều file. │ Trích xuất thành hàm hoặc module dùng chung.
3. Feature Envy         │ Phương thức truy cập dữ liệu class khác quá │ Chuyển phương thức về đối tượng sở hữu dữ
                        │ nhiều so với dữ liệu của chính nó.          │ liệu đó.
4. Data Clumps          │ Một nhóm tham số luôn đi cùng nhau qua hàm. │ Gom nhóm thành một kiểu dữ liệu riêng.
5. Primitive Obsession  │ Dùng chuỗi, số nguyên thủy cho khái niệm.   │ Đóng gói thành Branded Type hoặc Value Object.
6. Repeated Switches    │ Cùng một khối switch/if lặp lại ở nhiều nơi.│ Thay thế bằng Polymorphism hoặc Map/Lookup.
7. Shotgun Surgery      │ Một thay đổi nhỏ phải sửa rải rác nhiều file.│ Gom các thành phần liên quan vào một module.
8. Divergent Change     │ Một file bị sửa vì nhiều lý do không liên can│ Chia nhỏ module theo nguyên lý đơn trách nhiệm.
9. Speculative Generality│ Tạo tham số, abstraction phòng hờ tương lai.│ Xóa bỏ, giữ mã nguồn tối giản theo yêu cầu thật.
10. Message Chains      │ Chuỗi gọi phương thức quá dài a.b().c().d() │ Ẩn chuỗi truy cập sau phương thức trực tiếp.
11. Middle Man          │ Class chỉ đóng vai trò chuyển tiếp vô ích.  │ Cắt bỏ lớp trung gian, gọi trực tiếp đối tượng.
12. Refused Bequest     │ Class con từ chối hoặc override hầu hết kế  │ Thay thế Inheritance bằng Composition.
                        │ thừa từ class cha.                          │

4. Quy trình Giải quyết Merge Conflict

Khi làm việc trong môi trường thực tế, xung đột mã nguồn xuất hiện khi hai nhánh cùng chỉnh sửa một dòng hoặc khối lệnh so với điểm tổ tiên chung gần nhất (Merge Base). Quy trình 5 bước theo resolving-merge-conflicts:

🛠 5 Bước Giải quyết Merge Conflict
  1. Bước 1: Quan sát trạng thái hiện tại: Dùng git status để liệt kê các file bị xung đột (trạng thái unmerged UU). Kiểm tra vị trí các Conflict Markers (<<<<<<< HEAD, =======, >>>>>>>).
  2. Bước 2: Tìm nguồn gốc và ý định của từng bên: Đọc commit message, pull requests và issue tickets của cả hai nhánh để hiểu rõ mục tiêu kỹ thuật. Tránh phán đoán chủ quan.
  3. Bước 3: Giải quyết từng hunk:
    • Bảo toàn ý định của cả hai bên nếu tương thích (Preserve both intents).
    • Nếu bất tương thích, chọn bên phù hợp nhất với mục tiêu của việc merge và ghi chú lại sự đánh đổi.
    • Không tự ý bịa thêm hành vi mới ngoài phạm vi của hai nhánh.
    • Không dùng lệnh --abort do lúng túng.
  4. Bước 4: Chạy Automated Checks: Thực thi chuỗi kiểm tra tự động của dự án: Typecheck (tsc --noEmit), Tests (vitest run). Đảm bảo việc hòa giải không làm hỏng test case nào.
  5. Bước 5: Hoàn tất merge hoặc rebase: Đưa file đã sửa vào staging (git add) và tạo commit sáp nhập hoặc tiếp tục chu trình rebase.

5. Tình huống Thực tế: Xung đột giữa Audit Log và Atomic Lock

Hãy xem xét một tình huống xung đột thực tế khi hòa giải mã nguồn hàm commitReservation:

Conflict Hunk trong src/modules/inventory/adapters/supabase.ts
<<<<<<< HEAD (Nhánh feature/audit-logging)
  public async commitReservation(reservationId: ReservationId): Promise {
    const startTime = performance.now();
    console.log(`[AUDIT] Starting reservation commit: ${reservationId}`);
    const res = await this.getReservation(reservationId);
    if (!res) throw new ReservationNotFoundError(reservationId);
    // ... logic trừ kho cũ ...
    console.log(`[AUDIT] Reservation ${reservationId} committed in ${performance.now() - startTime}ms`);
  }
=======
  public async commitReservation(reservationId: ReservationId): Promise {
    // Nhánh feature/concurrency-fix: Chuyển sang gọi Stored Procedure nguyên tử
    const { error } = await this.client.rpc('commit_reservation_atomic', {
      p_reservation_id: reservationId,
    });
    if (error) {
      if (error.code === 'P0003') throw new ReservationNotFoundError(reservationId);
      throw new Error(`Atomic commit failed: ${error.message}`);
    }
  }
>>>>>>> feature/concurrency-fix
💡 Áp dụng Nguyên tắc Preserve Both Intents

Phân tích ý định:

  • Nhánh HEAD muốn: Bổ sung audit logging và đo đạc thời gian thực thi (Observability).
  • Nhánh feature/concurrency-fix muốn: Thay thế logic cũ bằng Stored Procedure nguyên tử để chống Race Condition (Data Integrity).

Hai ý định này hoàn toàn bổ trợ cho nhau. Đoạn mã hòa giải chuẩn mực sẽ bọc khối gọi RPC nguyên tử vào giữa cặp lệnh log thời gian thực thi, giữ trọn vẹn cả hai mục tiêu mà không làm mất đóng góp của bất kỳ lập trình viên nào.
