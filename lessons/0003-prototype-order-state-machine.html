Cách xây dựng mẩu thử độc lập để giải tỏa sự mơ hồ trong thiết kế logic trước khi tích hợp vào codebase chính.

Vòng đời đơn hàng không phải là một chuỗi tuần tự đơn giản. Nó liên kết chặt chẽ với cơ chế Stock Reservation with 15-min TTL, các sự kiện thanh toán, hủy đơn và xuất kho. Nếu lập tức tạo bảng Supabase, viết Server Actions và nối giao diện, bạn sẽ phải xử lý cùng lúc quá nhiều tầng phức tạp (Database, Network, Validation, Auth). Khi một edge case bị kẹt, chi phí sửa đổi toàn bộ các tầng này là rất lớn.

Kỹ năng /prototype giải quyết bài toán này: tạo Throwaway Code chỉ để trả lời dứt khoát một câu hỏi thiết kế duy nhất với chi phí thấp nhất.

1. Bản chất Kỹ nghệ của /prototype

Theo tài liệu gốc của Matt Pocock:

"A prototype is throwaway code that answers a question. The question decides the shape."
(Một prototype là mã nguồn dùng một lần để trả lời một câu hỏi. Chính câu hỏi sẽ quyết định hình dạng của prototype.)

Prototype được chia thành hai nhánh hoàn toàn khác biệt tùy thuộc vào bản chất câu hỏi:

Nhánh Câu hỏi Cần Trả Lời Artifact Shape
Logic Prototype
LOGIC.md		 "Mô hình trạng thái / logic nghiệp vụ này có hợp lý không?"
(Does this logic / state model feel right?)		 Một file HTML duy nhất, tự chứa toàn bộ CSS và JS, mở bằng double-click. Gồm một Pure Logic Module (Reducer), bảng hiển thị State trực quan, các nút Free-play và các kịch bản Guided Walkthroughs.
UI Prototype
UI.md		 "Giao diện này trông như thế nào?"
(What should this look like?)		 Nhiều biến thể giao diện (thường là 3 variants) trên cùng một route, chuyển đổi qua lại bằng tham số ?variant= và một thanh điều hướng nổi (floating bottom bar).
💡 Lựa chọn cho Bài 03: Logic Prototype

Mục tiêu của Bài 03 là kiểm chứng sự phối hợp giữa các trạng thái đơn hàng (DRAFT → PAID → SHIPPED → DONE / CANCELLED) và các ràng buộc tồn kho. Chúng ta không tìm kiếm bố cục giao diện, mà cần kiểm tra tính đúng đắn của các bước chuyển trạng thái (State Transitions). Do đó, chúng ta chọn nhánh Logic Prototype.

2. 6 Quy tắc Vàng khi Xây dựng Prototype

Matt Pocock đặt ra 6 nguyên tắc bất di bất dịch để giữ đúng bản chất của một prototype:

  1. Throwaway from day one: Code prototype sinh ra để học, không phải để tái sử dụng toàn bộ. Đặt tên rõ ràng (ví dụ: chứa tiền tố prototype) để người đọc không nhầm lẫn với production code.
  2. Trivial to run: Một Logic Prototype phải mở được bằng một cú double-click chuột trên trình duyệt. Không yêu cầu người khác phải chạy npm install, khởi động dev server hay cấu hình môi trường.
  3. No persistence by default: Toàn bộ State sống trong bộ nhớ RAM (in-memory). Database là thứ mà prototype đang chuẩn bị kiểm chứng, không phải thứ nó nên phụ thuộc vào.
  4. Skip the polish: Không viết unit tests cho prototype. Không xử lý lỗi vượt quá mức cần thiết để chạy. Không trừu tượng hóa sớm.
  5. Surface the state: Sau mỗi lần bấm nút hành động, giao diện phải lập tức hiển thị toàn bộ state liên quan bằng ngôn ngữ nghiệp vụ rõ ràng để người dùng nhìn thấy sự thay đổi.
  6. Capture it when done: Sau khi câu hỏi được trả lời, tích hợp phần Pure Logic Module đã được xác thực vào codebase chính; lưu prototype làm Primary Source đối chiếu.

3. Các Anti-patterns cần Tuyệt đối Tránh

⚠️ Những sai lầm thường gặp khi làm Prototype
  • Viết Unit Tests cho prototype: Khi bắt đầu viết test cho prototype, nó không còn là prototype nữa mà đã biến thành production code nửa vời.
  • Nối vào Database production: Gây tốn thời gian thiết lập schema, migrate dữ liệu và làm chậm vòng lặp phản hồi.
  • DOM coupling: Nếu các hàm tính toán trạng thái truy cập trực tiếp document.getElementById hoặc gắn liền với sự kiện click, bạn sẽ không thể tái sử dụng khối logic đó ở backend hoặc frontend.
  • Đưa cả file HTML của prototype vào Production: Giao diện prototype chỉ phục vụ việc kiểm thử thủ công. Chỉ có Pure Logic Module bên trong là tài sản có giá trị được giữ lại.

4. Phân tích Sản phẩm Thực tế: File Prototype Đơn hàng ERP

Chúng ta đã hiện thực hóa mẩu thử này tại prototypes/order-lifecycle-prototype.html. Hãy cùng bóc tách kiến trúc 2 tầng của file:

Tầng 1: Pure Logic Module độc lập

Toàn bộ logic chuyển trạng thái được đóng gói thành một Pure Reducer: (state, action) => newState. Hàm này hoàn toàn độc lập với DOM:

prototypes/order-lifecycle-prototype.html — Pure Reducer
// Pure function: Không truy cập DOM, không side-effect
function orderReducer(state, action) {
  const nextState = JSON.parse(JSON.stringify(state));

  switch (action.type) {
    case 'CREATE_DRAFT': {
      const qty = action.quantity;
      // Kiểm tra Invariant: Tồn kho khả dụng phải đủ
      if (nextState.inventory.availableStock < qty) {
        nextState.lastError = `Không đủ tồn kho khả dụng.`;
        return nextState;
      }
      // Giữ hàng: Tăng activeReservations, giảm availableStock
      nextState.inventory.activeReservations += qty;
      nextState.inventory.availableStock = nextState.inventory.physicalStock - nextState.inventory.activeReservations;
      nextState.order = { status: 'DRAFT', reservation: { status: 'ACTIVE' } };
      return nextState;
    }

    case 'CONFIRM_PAYMENT': {
      // Cam kết trừ vĩnh viễn vào kho vật lý khi thanh toán thành công
      const qty = nextState.order.quantity;
      nextState.inventory.physicalStock -= qty;
      nextState.inventory.activeReservations -= qty;
      nextState.order.status = 'PAID';
      nextState.order.reservation.status = 'COMMITTED';
      return nextState;
    }

    case 'CANCEL_ORDER': {
      // Chặn hành động bất hợp pháp: Không thể hủy đơn đã giao hoặc hoàn tất
      if (['SHIPPED', 'DONE'].includes(nextState.order.status)) {
        nextState.lastError = `HÀNH ĐỘNG BẤT HỢP PHÁP: Không thể hủy đơn khi đã ${nextState.order.status}.`;
        return nextState;
      }
      // Xử lý hoàn kho tương ứng nếu hủy từ DRAFT hoặc PAID
      ...
    }
  }
}

Tầng 2: Throwaway UI Shell

Bao bọc bên ngoài Pure Reducer là một giao diện trực quan hỗ trợ hai chế độ kiểm thử:

  • Free-play Buttons: Cho phép bấm các action theo thứ tự ngẫu nhiên để tìm ra các lỗi sơ hở trong logic.
  • Guided Walkthroughs: Cung cấp 4 kịch bản từng bước được lập trình sẵn để kiểm chứng các ca khó:
    1. Happy Path: Mua 2 sản phẩm → Giữ hàng 15 phút → Trả tiền và trừ tồn kho vật lý → Giao hàng → Hoàn tất.
    2. TTL Expired: Khách tạo đơn nhưng quá 15 phút chưa trả tiền → Hàng giữ tự động giải phóng, đơn về CANCELLED.
    3. Hủy đơn sau thanh toán: Tiền đã thu, kho đã trừ → Khách hủy đơn trước khi giao → Hệ thống chuyển trạng thái sang REFUNDED và hoàn lại tồn kho vật lý.
    4. Chặn thao tác bất hợp pháp: Thử bấm lệnh Hủy khi đơn đã xuất kho SHIPPED → State Machine từ chối và báo lỗi rõ ràng.
