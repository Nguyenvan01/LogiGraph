🌉 Bối cảnh kỹ thuật: Nguy cơ "Mục nát kiến trúc" (Architecture Erosion)

Ở Bài 07, chúng ta đã thiết kế Deep Module cho InventoryService với Interface 3 hàm. Tuy nhiên, trong thực tế, các dự án phần mềm thường bị Architecture Erosion: Theo thời gian, các lập trình viên (hoặc các AI agent thiếu định hướng) bắt đầu mở thêm các hàm getter phụ trợ, làm lộ các kiểu dữ liệu nội bộ ra ngoài, hoặc để mã nguồn tầng ứng dụng truy cập xuyên thấu vào database adapter.

Skill /improve-codebase-architecture cung cấp một quy trình kiểm toán kiến trúc khách quan: Quét codebase, tìm kiếm các Shallow Modules (mô-đun nông) và Leaky Abstractions, sau đó đề xuất các cơ hội Deepening (làm sâu mô-đun) thông qua báo cáo trực quan.

1. Bốn Trụ Cột Của Quá Trình Quét Kiến Trúc

Khi bạn kích hoạt /improve-codebase-architecture, agent thực hiện một quy trình phân tích 4 bước nghiêm ngặt:

Quy trình 4 bước của /improve-codebase-architecture
[1. Git Churn Hotspots] ──► [2. Deletion Test] ──► [3. Visual HTML Report] ──► [4. Grilling Loop]
   Quét tần suất sửa đổi        Đánh giá độ sâu         Biểu đồ phụ thuộc           Chất vấn & phê duyệt
   qua `git log --stat`         và Leaky Abstraction    Before vs After             kế hoạch Refactor
  • 1. Git Churn Hotspots: Sử dụng lệnh git log --stat -n 50 để xác định những file có tần suất thay đổi cao nhất kèm số lượng tác giả. Các file vừa có độ phức tạp cao vừa bị sửa liên tục chính là các "ổ rủi ro" (risk hotspots).
  • 2. The Deletion Test & Deepening: Đặt câu hỏi: "Nếu xóa bỏ module này, độ phức tạp sẽ biến mất hay bị đẩy sang nơi khác?". Nếu interface có quá nhiều hàm mỏng (shallow methods) chỉ để bọc lại database query, agent sẽ gom lại để nâng cao tỷ lệ đòn bẩy (Leverage).
  • 3. Báo cáo Visual HTML: Tạo file báo cáo trực quan (ví dụ: docs/architecture-report.html) chứa sơ đồ Mermaid thể hiện rõ luồng phụ thuộc trước và sau khi tối ưu.
  • 4. Vòng lặp Grilling Refactor: Phỏng vấn chất vấn lập trình viên về từng trade-off kiến trúc trước khi chạm vào mã nguồn thực tế.

3. Phân Tích Kết Quả: Báo Cáo Before vs After

Dưới đây là một phát hiện điển hình được agent chỉ ra trong báo cáo kiểm toán:

Phát hiện Leaky Abstraction và Phương án Deepening
❌ KIẾN TRÚC TRƯỚC TỐI ƯU (Shallow Module — Dễ rò rỉ):
┌────────────────────────────────────────────────────────┐
│ Caller (Server Action / Controller)                    │
│   1. Gọi repo.getProduct(id)                           │
│   2. Tự tính: if (product.stock < requested) throw...  │ ◄── Caller phải tự xử lý logic
│   3. Tự kiểm tra TTL 15 phút                           │ ◄── Rò rỉ nghiệp vụ ra ngoài
│   4. Gọi repo.updateStock(id, newStock)                │
└────────────────────────────────────────────────────────┘

✅ KIẾN TRÚC SAU KHI DEEPENING (Deep Module — Đóng gói hoàn hảo):
┌────────────────────────────────────────────────────────┐
│ Caller (Server Action / Controller)                    │
│   1. Gọi duy nhất: inventoryService.reserveStock(...)   │ ◄── Interface 1 dòng cực gọn
└────────────────────────────────────────────────────────┘
          │
          ▼
┌────────────────────────────────────────────────────────┐
│ InventoryService (Deep Implementation)                 │
│   - Tự động kiểm tra Invariants và số lượng tồn kho    │
│   - Tự động quản lý đồng hồ TTL 15 phút                │
│   - Tự động xử lý Atomic Transaction qua Adapter       │
└────────────────────────────────────────────────────────┘
💡 Lợi ích cốt lõi của Deepening

Sau khi được làm sâu (Deepening), caller không cần biết bất kỳ chi tiết cài đặt nào bên trong. Nếu sau này ta chuyển từ In-Memory Adapter sang PostgreSQL RPC hay Redis, toàn bộ code phía Server Actions và Frontend hoàn toàn không cần sửa đổi dù chỉ 1 ký tự.
